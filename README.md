# Supervised Grok lanes for RedOps

This repository packages the method used to run several Grok CLI investigations in parallel while preserving a reviewer-ready evidence trail. Each lane is **one independent Grok CLI process**, with its own assignment, session UUID, prompt, and state directory. These are parent-managed processes, not Grok's internal subagents.

The local `runner.py` starts and monitors Grok. Grok uses the RedOps MCP server for target commands and evidence. That supervisor never sends target traffic or calls the RedOps HTTP control plane. The separate `webchat_capture.py` browser adapter drives only its configured chatbot page and records the resulting exchange.

## How the pieces fit

| Piece | Job |
|---|---|
| Operator or parent agent | Pins the current engagement, splits distinct paths into lanes, reviews results, and decides what to pursue next. |
| `AGENTS.md` | Gives Grok a reusable authorized lab or exam role. It contains no target addresses. |
| `PROMPT_TEMPLATE.md` | Becomes a **private**, engagement-specific prompt for one lane. |
| `.grok/config.toml` | Connects Grok to the local RedOps MCP server; generated by `configure.py` and ignored by Git. |
| `runner.py` | Starts a detached process, records exact prompts/stdout/stderr, heartbeats, exit status, and optional same-session restart. |
| RedOps MCP | Captures target commands, outputs, attribution, facts, credentials, findings, and phase summaries. |
| REPORT case | Optionally receives the Grok AI exchange; target runs and screenshots are imported separately by stage. |

**A heartbeat means the process is alive.** It does not prove a target action or objective. For progress, inspect the RedOps feed, queue, and captured run output.

## Requirements and setup

- Linux with Python 3.11 or newer.
- A working Grok CLI. The CLI flags were tested with Grok `1.0.70`; verify them when upgrading.
- A local [RedOps](https://github.com/thomasmcinerney/redops-public) installation and a pinned, authorized engagement.

```sh
python3 configure.py --redops-dir /absolute/path/to/redops
grok --trust --cwd "$PWD" inspect --json
python3 test_runner.py
```

`configure.py` validates the RedOps Python and MCP server paths, then writes `.grok/config.toml` with absolute paths. That generated file is local only. Check `grok inspect --json` for this project's `AGENTS.md` and `redops` MCP server before launching a lane. Ask Grok to echo the `GROK-REDOPS-LAB-V1` marker; this confirms it loaded the guide.

## Launch independent lanes

Start with RedOps `session_brief`: confirm the current engagement, assigned targets, objectives, and guard state. Create a REPORT case and its target/stage before capture if you need a report. Fill `PROMPT_TEMPLATE.md` separately for each path. Store filled prompts under `private/` or another non-Git directory; they may contain credentials and proof values.

Give every lane a distinct state directory and session UUID. Use the same REPORT case for one engagement. For example:

```sh
python3 -c 'import uuid; print(uuid.uuid4())'

python3 runner.py start \
  --cwd "$PWD" \
  --state-dir "$PWD/private/lane-01" \
  --prompt-file "$PWD/private/lane-01.txt" \
  --session-id '<UNIQUE_UUID>' \
  --report-case /private/path/to/report-case \
  --report-module-dir /absolute/path/to/redops/report-kit \
  --max-turns 45 --max-restarts 1

python3 runner.py checkin --state-dir "$PWD/private/lane-01"
```

Omit **both** `--report-case` and `--report-module-dir` when you do not want REPORT integration. `start` returns after the detached supervisor has written its first state snapshot. Use `runner.py resume` with the **same** session UUID and a new prompt for a later phase. An abnormal Grok exit triggers at most `--max-restarts` same-session attempts; the resume prompt directs Grok to inspect prior RedOps runs before repeating anything.

The runner stores `state.json`, append-only `heartbeat.jsonl`, and each attempt's exact prompt, stdout, stderr, and final state under the lane directory. It creates run directories with mode `0700` and copies prompts with mode `0600`. Treat those files as engagement evidence and keep the state directory private.

## The lane loop

1. Grok reads `AGENTS.md`, calls RedOps `session_brief`, checks the feed and worklist, and confirms its runtime assignment.
2. It sets `focus_target` and passes an explicit `target_ip` on every target command. Focus is shared across lanes. Local diagnostics use `run(local=True)`.
3. It logs why it is testing, uses bounded target commands, records facts and negative controls, and separates claims from observations and verified exploitation.
4. At a phase boundary, import completed focused RedOps runs into the right REPORT target and stage. The optional runner integration records each Grok CLI attempt as an AI query event; that event does **not** automatically attribute target runs or screenshots.
5. Grok hands off exact RedOps run IDs, observed results, failed controls, the next evidence-backed lead, and any original proof path/value plus direct screenshot. The parent assigns a new path only after checking what other lanes already covered.

Give lanes distinct hypotheses instead of duplicating a broad scan. The runner has no global lane cap; practical concurrency depends on local CPU, Grok service limits, RedOps capacity, and target impact. Long target jobs belong in the RedOps background queue and must be polled by run ID. The local supervisor does not provide an outer wall-clock timeout or stall detector; `--max-turns` limits Grok turns, while `checkin` reports process state.

## What Grok can call

The tested runner starts Grok with project trust, the project `--cwd`, a prompt file, streaming JSON, RedOps MCP allowed, and `--no-subagents`. It denies direct Bash, WebFetch, WebSearch, and CaseHub calls. It does not blanket-deny every other MCP connector. Inspect the effective tool list and permission behavior after a Grok CLI upgrade; keep target actions on RedOps MCP so the command and output remain attributable.

## Browser chatbot capture

Use the browser adapter for a web chatbot whose interactions are outside Grok's
RedOps MCP command stream. It records exact scenario inputs, widget text, full
chat request/response bodies, WebSocket frames, screenshots, timestamps, and SHA-256
hashes under a private lane directory. Static resource responses retain headers,
byte counts, and hashes to keep a session manageable. Each lane has its own browser context.
The adapter requires the generic web scope and report bridge from redops-public.

Install Playwright in an isolated environment. Chromium may be supplied by the
system, as shown here:

~~~sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-webchat.txt
~~~

Create a RedOps engagement with an exact HTTPS page URL as its scope, then use
web_scope_set to add only observed messaging API prefixes if direct replay is
needed. A page URL permits browser interaction with that page; it does not
permit arbitrary API replay on the same host.

Create a private scenario JSON, for example:

~~~json
{
  "page_url": "https://chat.example.test/help",
  "actions": [
    {"type": "open"},
    {"type": "button", "text": "Provider"},
    {"type": "message", "text": "What can you help with?"}
  ]
}
~~~

Run one lane with its own output directory:

~~~sh
.venv/bin/python webchat_capture.py \
  --scenario private/lane-01.json \
  --out private/lane-01-capture \
  --redops-dir /absolute/path/to/redops-public \
  --engagement 1 \
  --browser-executable /usr/bin/chromium
~~~

The recorder fetches that engagement's web scope from RedOps and posts each
completed action to its capture endpoint. It stops if the page URL is outside
scope. Direct API actions require an explicitly configured API prefix; use the
browser flow to identify a messaging route before adding one. For a local test,
use --scope-file with the JSON returned by web_scope_show instead of
--engagement. Keep actual prompts, cookies, and captures under private/.

For a report case with a target and stage already created, add
--report-case, --report-module-dir, --target, and --stage. The importer copies
the exact network transcript and direct screenshot for every action into the
case, with stable source IDs so reimporting is safe.

A blocked page or failed browser action leaves `manifest.json` with the error,
page text, network transcript, and failure screenshot. When an engagement is
selected, that failed action is also posted to RedOps as a `webchat` event and
can be imported into the report case. Some sites challenge
headless browsers; review that evidence and complete any interactive verification
in a headed browser session (`--headed`) rather than treating the
challenge as a chatbot finding. A headed lane waits up to two minutes for the
widget launcher after an HTTP error page; the operator must complete the
verification in that visible browser. Each lane uses a fresh browser context. The generic mock test runs with `.venv/bin/python -m unittest -q
test_webchat_capture` and exercises both a completed exchange and a 403.

The recorder's main-frame navigation is confined to the exact configured page.
Its embedded widget loads its normal vendor resources. It only submits
scenario actions to the widget or to configured API prefixes. Use separate
browser contexts for independent lanes and keep each lane on a distinct
hypothesis.

## Report and shutdown

Use direct target output and screenshots for proofs. Keep exact commands, output, AI prompts/responses, scripts, and modifications in the REPORT case. Review the generated PDF and run the report gate before submission.

```sh
python3 runner.py stop --state-dir "$PWD/private/lane-01"
python3 runner.py checkin --state-dir "$PWD/private/lane-01"
```

`stop` terminates the Grok child process group. It does **not** cancel RedOps background target jobs, stop SSH tunnels created by the engagement, or undo target-side changes. Check the RedOps queue and terminate only confirmed engagement-owned processes before shutting a lab down.

The network-free `test_runner.py` checks launch, same-session resume, raw prompt/output retention, heartbeat, optional REPORT adapter invocation, and stop.
